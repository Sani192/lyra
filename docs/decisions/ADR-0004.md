# ADR-0004: Why Lyra Needs a Capability Registry

## Maturity Metadata

**Status:** Approved.

**Intended Use:** Authoritative architecture decision; safe for implementation decisions within its documented scope.

## Status

Accepted.

## Context

At runtime, Lyra's Conversation and Workflow Engines must dynamically discover what capabilities are available for a given project to satisfy user intents.

## Problem

Hardcoding capabilities or configuration tables prevents runtime extensions and multi-tenant scaling.

## Options Considered

1. **Static Project Configuration:** Configure available capabilities in local JSON/YAML configuration tables per project. Rejected because it prevents dynamic registration and runtime updates of consumer contracts.
2. **Distributed/Dynamic Discovery:** Query the consumer application at every conversational turn to ask what capabilities it supports. Rejected due to latency, network overhead, and loss of registry-side schema caching.
3. **Centralized Capability Registry:** Maintain a central component in Lyra that caches registered contracts, indexes capabilities by intent, and validates request payloads against cached schemas. Accepted.

## Decision

Implement a centralized Capability Registry component within the Lyra platform to manage registered contracts, cache schemas, and coordinate tool lookups.

## Consequences

* **Dynamic Discovery:** Consumer applications can register or update contracts without restarting Lyra services.
* **Low Latency:** Capability schemas are cached locally in the registry, avoiding network roundtrips for validation.
* **Intent-to-Tool Mapping:** The AI Agent Layer can query the registry to fetch only the capabilities matching the active conversational intent.

## Future Considerations

Implement caching mechanisms (e.g. Redis or in-memory LRU) in the registry for contract lookup optimization.
