# ADR-0005: Why REST, OpenAPI, and MCP Are First-Class Protocols

## Maturity Metadata

**Status:** Approved.

**Intended Use:** Authoritative architecture decision; safe for implementation decisions within its documented scope.

## Status

Accepted.

## Context

Lyra must integrate with external services built using different programming languages, API patterns, and runtime frameworks.

## Problem

Enforcing a single proprietary protocol or format restricts integration options and increases friction for consumer adoption.

## Options Considered

1. **Proprietary gRPC/Protobuf Protocol Only:** Expose capabilities only via gRPC. Rejected because although high-performance, it adds development complexity for standard web developers.
2. **REST/OpenAPI Only:** Expose endpoints strictly through REST and OpenAPI schemas. Rejected because it lacks native support for agentic tool use (such as dynamic model-controlled local command executions).
3. **Multi-Protocol Adapter Layer (REST, OpenAPI, and MCP):** Support REST/OpenAPI for standard web services and Model Context Protocol (MCP) for agentic and tool-based integrations. Accepted.

## Decision

Design Lyra's Protocol Layer as a pluggable adapter system supporting REST, OpenAPI, and MCP as first-class integration protocols.

## Consequences

* **High Interoperability:** Almost any modern backend can expose capabilities to Lyra via REST.
* **Agentic Tool Support:** Native MCP integration enables state-of-the-art LLM tools to coordinate directly with Lyra.
* **Autogenerated Clients:** OpenAPI imports allow Lyra to autogenerate client request validators.

## Future Considerations

Implement protocol-specific middleware (e.g. security sanitization, rate-limiting) inside each adapter module.
